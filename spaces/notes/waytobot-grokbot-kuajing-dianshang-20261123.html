Grok Bot 跨境电商实战：1 个主管 + 12 个 Agent 岗位

X Space（WayToBot 社区）· 主持：蓝哥AI（@0xlangeai）· 主讲：扎斯老师（前亚马逊团队负责人）· 2026-11-23 19:56 开播 · 时长约 107 分钟

说明：本场录音的自动转写噪声较大——产品名 Grok Bot 在转写里有十几种写法，嘉宾名以主持人口播的「扎斯老师」为准（转写中另有 Zack、Jack 等写法，应为同一人）。文中数字均为发言者自述，未经外部核实；约 00:49–00:50 有约 38 秒转写缺失；录音在结尾的自由交流中途结束。

一句话

一位把亚马逊团队两年做到 2 亿 GMV 的操盘手，分享他怎么把 Grok Bot 搭成「1 个主管 + 12 个岗位 Agent」的运营团队：先接付费数据接口、再沉淀自有 Skill、产出全部回写飞书；后半场的开放麦则聊透了利润打法、欧洲税务和 GEO 新流量。

主讲部分：扎斯老师的 Grok Bot 落地方法（约 00:05–00:42）

扎斯老师的背景（主持人介绍）：曾负责带公司的整个亚马逊团队，约两年从 0 到 1 做到两个亿 GMV；2025 年 7 月离职创业，现做企业咨询陪跑，同时自己选品。

他对 Grok Bot 的定位：本质是「一个大号的龙虾」——平台帮你配好了模型和云电脑，形态上更适合做执行层；但它不能自选模型，所以真正的打法是多 Agent 搭配。他的六个要点：

1. 先给 Agent 接准数据：三类付费接口

不要让 Bot 去云电脑上抓亚马逊前台——他们 9 月试过还能进，10 月就被亚马逊前台机制挡住了，效果也不理想。应该接付费 API，分三类：

  • 自有店铺数据：领星、赛狐等跨境 ERP 已经出了对应的 MCP 接口，接进来 Agent 才知道每条链接的真实销售情况；
  • 市场调研数据：H10、卖家精灵、Sorftime 等第三方工具的数据（近半年基本都开放了 MCP 或 CLI），基于真实平台数据做调研，而不是基于报告猜；
  • 关键词数据：SIF、西柚洞察一类关键词服务商，监控具体链接的关键词表现。

三类数据接齐，店铺和大盘的分析能扎实约 90%；剩下的众筹等长尾数据同样找付费接口，不要硬抓。

2. 每家公司必须有自己的 Skill（工作流）

直接让 Bot 裸跑任务，结果往往跟想要的不一样；把成熟做法写成 Skill 给它执行，才可能真正替代掉某个岗位的工作。他们的做法是本地 + 云端分工：用本地的 Claude Code、Codex、Google Antigravity 写 Skill，统一放在 GitHub，Grok Bot 从同一仓库拉取执行，本地和云端共用同一套 Skill、在实战中迭代。再给 Grok Bot 一个单独的 GitHub 账号提交 PR，区分哪些改动是 Bot 自己提的、哪些是本地 Agent 提的，改崩了能回滚。

同理，市场调研这类任务的 Skill 必须带上公司的目的：他上一家公司只看规模、不看利润率（为做 GMV 上市），调研就优先看市场体量；自己创业后反过来，优先看切入的利润率。目的不同，Skill 就不同——这是 Skill 不能照搬的根本原因。

3. 给 Grok Bot 装 Codex CLI，补它的短板

Grok Bot 不能选模型，处理大数据量任务（比如抓亚马逊榜单 Top 100 做挖掘）效果不好。解法：在 Grok Bot 里装好 Codex CLI，设一个专管数据分析的 Bot，遇到大数据处理就调用 Codex 来执行，效果明显好于让它靠自带模型硬做。

4. 产出全部回写飞书，资产留在公司内部

一定要打通飞书协作，把 Agent 的产出回写到公司内部服务器或飞书知识库，而不是留在云端电脑里。理由很现实：哪天 Grok Bot 降智了、或者有更好的产品出现，迁移成本取决于资料在不在自己手里。团队成员哪怕不用 Grok Bot，在飞书里也能读到全部产出、接着推进。

5. 岗位架构：1 + N，不要群聊

他搭了 12 个岗位 Bot + 1 个亚马逊主管 Bot，按「向外看 / 向内看 / 流量侧 / 支撑侧」分工：

  • 向外看：跨境情报 Bot，盯亚马逊和美国市场的趋势变化，反哺自家 Listing；
  • 向内看：VOC 反馈 Bot + 运营数据分析 Bot，看产品上架后的真实问题；
  • 内容生产：文案 Bot、图片 Bot（接 Nano Banana 模型出图）各一；
  • 流量侧：广告策略 Bot（横看 Google、Meta、亚马逊 DSP 等跨平台流量）+ 亚马逊广告投手 Bot（只处理站内广告报表）；
  • 支撑侧：库存 Bot、物流时效 Bot、财务 Bot（盯每条链接的利润率，出周报月报）、合规 Bot（抓合规政策做上架前把关，如磁吸类产品限制、认证要求）；
  • 闭环：还有一个 Bot 专管周报月报，把做对和做错的经验沉淀进内部知识库。

两个细节值得记：

  • 数据分析为什么拆成三个 Bot：最早所有报告都塞给一个「运营数据分析」Bot，后来把广告数据和财务数据单独拆出来各设一个 Bot 做上下文隔离——因为他们是精品出身，认定广告和财务是亚马逊生意里最重要的两块，值得精细化；运营分析 Bot 则回归看流量、链接详情页数据并做汇总。
  • VOC 的数据困境：亚马逊原本有 SP-API 接口能拿到自家店铺的 review 数据，约在 2025 年七八月把这个接口关了，领星等 ERP 现在也拿不到 review 数据。他们现在的办法是手动抓最新评论、存回内部，再让 Agent 分析——他建议真重视 VOC 的卖家在评论上多下功夫，AI 能把评论挖得比以前深得多。

整套体系沉淀了六七十个 Skill，分配给各 Bot（每个 Bot 底下三五个），全链路从选品、文案、上架、广告策略与投放、库存到财务，都在飞书里流转推进。

6. 照搬框架的翻车现场

他把这套框架分享给社群朋友后，有人直接全盘照搬，把写文案、选品、财务几个 Bot 拉进一个群——结果几个 Bot 纷纷发言「这件事情不归我管，我要退群」。教训就是上面的架构原则：按任务分工、明确边界，不要用群聊把 Bot 混在一起；框架只能借鉴思路，每家公司的业务形态不同，不能原样搬。

关于「降智」与多 Agent 搭配

扎斯说 Grok Bot 最近一两个月有明显的降质：9 月时觉得特别好用、想把所有工作都迁进去，用下来发现更落地的场景还是多 Agent 搭配——本地 Agent 写 Skill、云端 Bot 执行，手机上也能把事办了；团队成员 Skill 不完善也没关系，直接在飞书里 @ 对应的 Bot 就能干活。

开放麦精选（约 00:42–01:47）

评论爬取的土办法

一位听众分享：装一个走 CDP 的浏览器操控 Skill，让 Agent 像真人一样操控本地浏览器爬评论，本地 IP 基本不触发封控（亚马逊、沃尔玛、Reddit 都试过）；扎斯补充：云端浏览器登录亚马逊看评论可以，但批量抓会触发风控。双方约了私下细聊。

生意账：利润率、FBA 与认证

  • 利润率打法：早期纯贸易时 15 个点以上没什么问题；上一家工贸一体公司纯追求规模，故意把利润率压到 10% 以下、投放打得很激进，「就是不想让竞争对手进来」，第二年做到 2 亿多 GMV——按 10% 算也是两千多万利润（均为自述）；
  • 仓配：大部分货直发 FBA，少量库存放海外仓应急，不太需要自建海外仓；
  • 认证：大多数产品用供应商现成的认证、让供应链发证书即可；纯私模产品才需要自己找机构做；
  • 他为什么出来创业：和公司谈股权没谈拢（自述）；也有老板挖他，但「过去还是打工」，职场收入上限和成就感都有限；
  • 创业的现金流安排：亚马逊资金周转差、特别压钱，所以他一边给底子弱的跨境企业做咨询陪跑、接广告代投拿现金流，一边自己选品，选品偏供应链整合，不靠 1688 铺货。

欧洲税务：别全灰

德国卖家 Aurora（在德国的华人团队，做 TikTok、Temu、Otto 等本土平台，有服饰美妆 3C 货盘和海外仓，资质齐全）问合作与品类偏好，扎斯的回应里带出欧洲站的门槛：

  • 泛欧计划要把欧洲五国税号注册完，得十几万，小卖家拿不出；他们在欧洲只挑小品类做更高利润率，主力仍是美国，欧洲多是拿美国的产品过去卖；
  • Aurora 补充实操：现在不一定要注册五国，一般一个公司主体配套两个税号（本国 + 欧盟），如德国主体就是德国税号 + 欧盟税号；并提醒不要全灰——看好、利润高的货必走正规清关，全灰在后续税务、记账报税上麻烦很多；德国税局前几年发起过针对中国卖家的调查、封了不少卖家，税局很清楚中国卖家在玩什么；
  • 扎斯早前被问到国内物流的双清包税时也说：行业里不少利润本质上是偷漏税的钱，合规申报后很多账算不过来（此段发言有约 38 秒转写缺失，观点以缺失前后语境为准）；
  • 品类上，移动空调今年在欧洲卖到断货、Aurora 团队已在备货明年夏天；扎斯说这类品类想碰，但现阶段资金量不够。合作意向双方都有，约了会后细聊。主持人蓝哥也在现场拉了跨境电商微信群。

多 Agent 协同：飞书做中枢，人做拍板

飞书渠道方的王先生（SaaS 出身）问：一个任务要多个 Agent 接力时怎么自动协调？扎斯的答案很克制：

  • 不追求全链路自动化。他们还在打磨阶段，关键节点坚持 Human in the loop——「做跨境电商都是真金白银砸下去」，最后必须有人确认；确认的过程本身就是在打磨 Skill 和工作流，把返工率压低，但最终拍板留给人；
  • 体系与其说搭在 Grok Bot 上，不如说搭在飞书上：所有 Agent 的产出都回飞书，换任何 Agent（Grok Bot、Codex、Claude Code）都能接着往下推进；
  • 王先生分享了自己的版本：花一周做了个工作台，看每个任务的执行节点和自动化结果，在工作台上提交反馈、由一个 GPT 侧的 Agent 捕捉后分发调整给各个 Bot——他自评是个复杂工程，「不知道未来能有什么用，挺好玩的」。

工具打通：CLI + Skill + 飞书机器人换后端

  • 听众阿健问 Grok Bot 与 Claude、Gemini 等怎么打通联动，扎斯答：用 CLI（在 Grok Bot 里装 Codex CLI）+ 用 Skill 统一行为，Skill 在 GitHub 统一管理，谁执行时发现 Skill 不好就迭代，Grok Bot 定期拉取更新；最终结果沉淀飞书，中间沟通的优先级低于结果本身；
  • 铁柱补充：飞书机器人可以接不同的 Agent 后端——GitHub 上有开源项目，能把 Claude Code、Antigravity、Codex 乃至国产 Agent 都接进飞书机器人，于是文案岗可以配 Gemini 或 Kimi、做图岗配 Codex，按岗位最大化利用各模型长处；他还提到 Gemini 最新模型很强，已经成了 Claude 的平替（均为发言者观点）。

知识库要能自进化

  • 铁柱写过一套基于 LLM Wiki + Hermes 的知识库搭建教程（公众号文章），特点是知识库可以自我进化，会发到群里；
  • 王先生的做法：设一个「知识库管理员」Agent 做两道质检——外部信息入库前先审值不值得存、价值在哪；已入库内容里的废弃材料定期检索删除；
  • 传统外贸出身的塞特咖（自研系统给四个厂家做跨境，跑 GEO/SEO/EDM，客户走 WhatsApp 沟通）强调 RAG 的误区：不是投喂越多越好，文档进来必须去重、清洗、去噪，Agent 调用的答案才会越来越准；他的知识库按厂家和产品线分区（产品库、客服库等），客户咨询时由对应 Agent 调取后人工转述回复。他自 2025 年 9 月给第一个客户上独立站系统，自述流量基本全是 GEO 带的，并晒了 24 小时后台数据：必应 460 多、谷歌 200 多、苹果端 120 多（客户做实验室玻璃仪器、卖欧美）；
  • 他还提醒选品先看品类壁垒：实验室仪器这类产品国外认证成本极高、欧美渠道基本被三大分销商占住，品牌再好也很难挤进去；户外用品这类就好做得多。

GEO：被反复提到的新流量入口

品牌出海公司的 Tim 分享了两个项目：

  • GEO 项目：上一家公司独立站做 GEO 约三个月，AI 带来的流量翻了一倍、营收涨了约 50%（自述）。要点：GEO 的地基是 SEO——先把 SEO 做到同行第一第二，再做 GEO 是事半功倍；北美市场 AI 流量的主要入口是 ChatGPT，他们先挖出客户会在 AI 上问的一两百个细分问题（比如「新手最值得买的高级机是什么」「亚克力场景该买哪个料理机」），再针对性优化官网、Reddit、YouTube、维基百科等 ChatGPT 爱抓的渠道（他们当时连维基百科词条都没有，赶紧补上）；
  • VOC 舆情系统：把亚马逊、各社交平台、Reddit 等全渠道的用户评论（买过的和没买的）统一抓回，用大模型打标分类（售前问题、售后问题、对哪个产品有疑问），再分流到售后工单或售前咨询；沉淀下来的数据对后续选品和产品迭代价值很大；
  • 主持人补充：在刚结束的 GEO 大会上有嘉宾分享，豆包采集最多的视频时长是 5 分钟的视频（不是通常以为的长视频）；海外做 GEO 的会买词、做 PR，动辄几千个词。在流量越来越贵的环境里，GEO 仍能拉到相对低成本的流量。

一句话收尾

这场最值钱的不是某个工具技巧，而是两个判断：一，Agent 团队的上限取决于你喂的数据接口和沉淀的 Skill，而不是模型本身；二，越是真金白银的业务，越要把「人做最终确认」写进流程里。

主講部分：扎斯老師的 Grok Bot 落地方法（約 00:05–00:42）

扎斯老師的背景（主持人介紹）：曾負責帶公司的整個亞馬遜團隊，約兩年從 0 到 1 做到兩個億 GMV；2025 年 7 月離職創業，現做企業諮詢陪跑，同時自己選品。

他對 Grok Bot 的定位：本質是「一個大號的龍蝦」——平台幫你配好了模型和雲端電腦，形態上更適合做執行層；但它不能自選模型，所以真正的打法是多 Agent 搭配。他的六個要點：

1. 先給 Agent 接準數據：三類付費接口

不要讓 Bot 去雲端電腦上抓亞馬遜前台——他們 9 月試過還能進，10 月就被亞馬遜前台機制擋住了，效果也不理想。應該接付費 API，分三類：

  • 自有店鋪數據：領星、賽狐等跨境 ERP 已經出了對應的 MCP 接口，接進來 Agent 才知道每條連結的真實銷售情況；

  • 關鍵詞數據：SIF、西柚洞察一類關鍵詞服務商，監控具體連結的關鍵詞表現。

三類數據接齊，店鋪和大盤的分析能紮實約 90%；剩下的眾籌等長尾數據同樣找付費接口，不要硬抓。

2. 每家公司必須有自己的 Skill（工作流）

直接讓 Bot 裸跑任務，結果往往跟想要的不一樣；把成熟做法寫成 Skill 給它執行，才可能真正替代掉某個崗位的工作。他們的做法是本地 + 雲端分工：用本地的 Claude Code、Codex、Google Antigravity 寫 Skill，統一放在 GitHub，Grok Bot 從同一倉庫拉取執行，本地和雲端共用同一套 Skill、在實戰中迭代。再給 Grok Bot 一個單獨的 GitHub 帳號提交 PR，區分哪些改動是 Bot 自己提的、哪些是本地 Agent 提的，改崩了能回滾。

同理，市場調研這類任務的 Skill 必須帶上公司的目的：他上一家公司只看規模、不看利潤率（為做 GMV 上市），調研就優先看市場體量；自己創業後反過來，優先看切入的利潤率。目的不同，Skill 就不同——這是 Skill 不能照搬的根本原因。

3. 給 Grok Bot 裝 Codex CLI，補它的短板

Grok Bot 不能選模型，處理大數據量任務（比如抓亞馬遜榜單 Top 100 做挖掘）效果不好。解法：在 Grok Bot 裡裝好 Codex CLI，設一個專管數據分析的 Bot，遇到大數據處理就調用 Codex 來執行，效果明顯好於讓它靠自帶模型硬做。

4. 產出全部回寫飛書，資產留在公司內部

一定要打通飛書協作，把 Agent 的產出回寫到公司內部伺服器或飛書知識庫，而不是留在雲端電腦裡。理由很現實：哪天 Grok Bot 降智了、或者有更好的產品出現，遷移成本取決於資料在不在自己手裡。團隊成員哪怕不用 Grok Bot，在飛書裡也能讀到全部產出、接著推進。

5. 崗位架構：1 + N，不要群聊

他搭了 12 個崗位 Bot + 1 個亞馬遜主管 Bot，按「向外看 / 向內看 / 流量側 / 支撐側」分工：

  • 向外看：跨境情報 Bot，盯亞馬遜和美國市場的趨勢變化，反哺自家 Listing；
  • 向內看：VOC 反饋 Bot + 運營數據分析 Bot，看產品上架後的真實問題；
  • 內容生產：文案 Bot、圖片 Bot（接 Nano Banana 模型出圖）各一；
  • 流量側：廣告策略 Bot（橫看 Google、Meta、亞馬遜 DSP 等跨平台流量）+ 亞馬遜廣告投手 Bot（只處理站內廣告報表）；
  • 支撐側：庫存 Bot、物流時效 Bot、財務 Bot（盯每條連結的利潤率，出週報月報）、合規 Bot（抓合規政策做上架前把關，如磁吸類產品限制、認證要求）；
  • 閉環：還有一個 Bot 專管週報月報，把做對和做錯的經驗沉澱進內部知識庫。

兩個細節值得記：

  • 數據分析為什麼拆成三個 Bot：最早所有報告都塞給一個「運營數據分析」Bot，後來把廣告數據和財務數據單獨拆出來各設一個 Bot 做上下文隔離——因為他們是精品出身，認定廣告和財務是亞馬遜生意裡最重要的兩塊，值得精細化；運營分析 Bot 則回歸看流量、連結詳情頁數據並做彙總。
  • VOC 的數據困境：亞馬遜原本有 SP-API 接口能拿到自家店鋪的 review 數據，約在 2025 年七八月把這個接口關了，領星等 ERP 現在也拿不到 review 數據。他們現在的辦法是手動抓最新評論、存回內部，再讓 Agent 分析——他建議真重視 VOC 的賣家在評論上多下功夫，AI 能把評論挖得比以前深得多。

整套體系沉澱了六七十個 Skill，分配給各 Bot（每個 Bot 底下三五個），全鏈路從選品、文案、上架、廣告策略與投放、庫存到財務，都在飛書裡流轉推進。

6. 照搬框架的翻車現場

他把這套框架分享給社群朋友後，有人直接全盤照搬，把寫文案、選品、財務幾個 Bot 拉進一個群——結果幾個 Bot 紛紛發言「這件事情不歸我管，我要退群」。教訓就是上面的架構原則：按任務分工、明確邊界，不要用群聊把 Bot 混在一起；框架只能借鑑思路，每家公司的業務形態不同，不能原樣搬。

關於「降智」與多 Agent 搭配

扎斯說 Grok Bot 最近一兩個月有明顯的降質：9 月時覺得特別好用、想把所有工作都遷進去，用下來發現更落地的場景還是多 Agent 搭配——本地 Agent 寫 Skill、雲端 Bot 執行，手機上也能把事辦了；團隊成員 Skill 不完善也沒關係，直接在飛書裡 @ 對應的 Bot 就能幹活。

多 Agent 協同：飛書做中樞，人做拍板

飛書渠道方的王先生（SaaS 出身）問：一個任務要多個 Agent 接力時怎麼自動協調？扎斯的答案很克制：

  • 不追求全鏈路自動化。他們還在打磨階段，關鍵節點堅持 Human in the loop——「做跨境電商都是真金白銀砸下去」，最後必須有人確認；確認的過程本身就是在打磨 Skill 和工作流，把返工率壓低，但最終拍板留給人；

  • 王先生分享了自己的版本：花一週做了個工作台，看每個任務的執行節點和自動化結果，在工作台上提交反饋、由一個 GPT 側的 Agent 捕捉後分發調整給各個 Bot——他自評是個複雜工程，「不知道未來能有什麼用，挺好玩的」。

工具打通：CLI + Skill + 飛書機器人換後端

  • 聽眾阿健問 Grok Bot 與 Claude、Gemini 等怎麼打通聯動，扎斯答：用 CLI（在 Grok Bot 裡裝 Codex CLI）+ 用 Skill 統一行為，Skill 在 GitHub 統一管理，誰執行時發現 Skill 不好就迭代，Grok Bot 定期拉取更新；最終結果沉澱飛書，中間溝通的優先級低於結果本身；
  • 鐵柱補充：飛書機器人可以接不同的 Agent 後端——GitHub 上有開源項目，能把 Claude Code、Antigravity、Codex 乃至國產 Agent 都接進飛書機器人，於是文案崗可以配 Gemini 或 Kimi、做圖崗配 Codex，按崗位最大化利用各模型長處；他還提到 Gemini 最新模型很強，已經成了 Claude 的平替（均為發言者觀點）。

知識庫要能自進化

  • 鐵柱寫過一套基於 LLM Wiki + Hermes 的知識庫搭建教學（公眾號文章），特點是知識庫可以自我進化，會發到群裡；
  • 王先生的做法：設一個「知識庫管理員」Agent 做兩道質檢——外部資訊入庫前先審值不值得存、價值在哪；已入庫內容裡的廢棄材料定期檢索刪除；
  • 傳統外貿出身的塞特咖（自研系統給四個廠家做跨境，跑 GEO/SEO/EDM，客戶走 WhatsApp 溝通）強調 RAG 的誤區：不是投餵越多越好，文件進來必須去重、清洗、去噪，Agent 調用的答案才會越來越準；他的知識庫按廠家和產品線分區（產品庫、客服庫等），客戶諮詢時由對應 Agent 調取後人工轉述回覆。他自 2025 年 9 月給第一個客戶上獨立站系統，自述流量基本全是 GEO 帶的，並曬了 24 小時後台數據：必應 460 多、谷歌 200 多、蘋果端 120 多（客戶做實驗室玻璃儀器、賣歐美）；

GEO：被反覆提到的新流量入口

品牌出海公司的 Tim 分享了兩個項目：

  • GEO 項目：上一家公司獨立站做 GEO 約三個月，AI 帶來的流量翻了一倍、營收漲了約 50%（自述）。要點：GEO 的地基是 SEO——先把 SEO 做到同行第一第二，再做 GEO 是事半功倍；北美市場 AI 流量的主要入口是 ChatGPT，他們先挖出客戶會在 AI 上問的一兩百個細分問題（比如「新手最值得買的高級機是什麼」「亞克力場景該買哪個料理機」），再針對性優化官網、Reddit、YouTube、維基百科等 ChatGPT 愛抓的渠道（他們當時連維基百科詞條都沒有，趕緊補上）；
  • VOC 輿情系統：把亞馬遜、各社交平台、Reddit 等全渠道的用戶評論（買過的和沒買的）統一抓回，用大模型打標分類（售前問題、售後問題、對哪個產品有疑問），再分流到售後工單或售前諮詢；沉澱下來的數據對後續選品和產品迭代價值很大；
  • 主持人補充：在剛結束的 GEO 大會上有嘉賓分享，豆包採集最多的影片時長是 5 分鐘的影片（不是通常以為的長影片）；海外做 GEO 的會買詞、做 PR，動輒幾千個詞。在流量越來越貴的環境裡，GEO 仍能拉到相對低成本的流量。

一句話收尾

這場最值錢的不是某個工具技巧，而是兩個判斷：一，Agent 團隊的上限取決於你餵的數據接口和沉澱的 Skill，而不是模型本身；二，越是真金白銀的業務，越要把「人做最終確認」寫進流程裡。

In One Sentence

An operator who grew an Amazon team to 200 million GMV in two years shares how he built Grok Bot into an operations team of "1 manager + 12 role-based Agents": first wire it up to paid data APIs, then accumulate your own Skills, and write all output back to Feishu; the open-mic second half thoroughly covered margin tactics, European taxes, and the new GEO traffic.

Main Talk: Zasi's Method for Putting Grok Bot to Work (approx. 00:05–00:42)

Zasi's background (per the host's introduction): he led his company's entire Amazon team, growing it from 0 to 1 to 200 million GMV in about two years; he left in July 2025 to start his own business, and now does corporate consulting and coaching while also selecting products himself.

His take on what Grok Bot is: essentially "an oversized lobster" — the platform pre-configures the models and a cloud computer for you, and its form makes it better suited as an execution layer; but it cannot choose models itself, so the real play is combining multiple Agents. His six points:

1. First, Give the Agent the Right Data: Three Kinds of Paid APIs

Don't have the Bot scrape Amazon's storefront from a cloud computer — they tried in September and could still get in, but by October Amazon's storefront mechanisms blocked them, and the results weren't great anyway. Instead, connect paid APIs, in three categories:

  • Your own store data: cross-border ERPs such as Lingxing and Saihu already offer corresponding MCP interfaces; once connected, the Agent knows the real sales picture of every listing;
  • Market research data: data from third-party tools such as H10, SellerSprite, and Sorftime (most have opened up MCP or CLI access in the last six months), so research is based on real platform data rather than guesswork from reports;
  • Keyword data: keyword service providers such as SIF and Xiyou Insight, to monitor the keyword performance of specific listings.

With all three kinds of data connected, analysis of your store and the overall market can be about 90% solid; for the remaining long-tail data such as crowdfunding, likewise find paid APIs instead of forcing a scrape.

2. Every Company Must Have Its Own Skills (Workflows)

If you let the Bot run tasks bare, the results often aren't what you wanted; writing proven practices into Skills for it to execute is what makes it possible to truly replace the work of a given role. Their approach splits local and cloud: they write Skills locally with Claude Code, Codex, and Google Antigravity, keep them all in GitHub, and Grok Bot pulls from the same repository to execute them, so local and cloud share one set of Skills and iterate on them in real work. They also gave Grok Bot its own GitHub account for submitting PRs, to distinguish which changes the Bot proposed itself and which came from local Agents, so a bad change can be rolled back.

Likewise, a Skill for a task like market research must carry the company's purpose: his previous company cared only about scale, not margins (doing GMV in order to go public), so research prioritized market size; after starting his own business he reversed that, prioritizing the margin at which he can enter a market. Different purpose, different Skill — that is the fundamental reason Skills cannot simply be copied.

3. Install the Codex CLI in Grok Bot to Cover Its Weakness

Grok Bot cannot choose models, and it performs poorly on large-data tasks (such as scraping and mining Amazon's Top 100 charts). The fix: install the Codex CLI inside Grok Bot, set up a Bot dedicated to data analysis, and have it call Codex for heavy data processing — the results are markedly better than letting it grind through with its built-in model.

4. Write All Output Back to Feishu, So the Assets Stay Inside the Company

You must connect Feishu collaboration and write the Agents' output back to internal company servers or the Feishu knowledge base, rather than leaving it on the cloud computer. The reason is practical: if one day Grok Bot gets dumber, or a better product appears, the migration cost depends on whether the materials are in your own hands. Even team members who don't use Grok Bot can read all the output in Feishu and carry the work forward.

5. Role Architecture: 1 + N, No Group Chats

He built 12 role Bots + 1 Amazon manager Bot, divided by "looking outward / looking inward / traffic side / support side":

  • Looking outward: a cross-border intelligence Bot that watches trend changes on Amazon and in the US market and feeds them back into their own Listings;
  • Looking inward: a VOC feedback Bot + an operations data analysis Bot, watching for real problems after products go live;
  • Content production: one copywriting Bot and one image Bot (connected to the Nano Banana model for image generation);
  • Traffic side: an advertising strategy Bot (looking across Google, Meta, Amazon DSP and other cross-platform traffic) + an Amazon ads Bot (handling only on-site ad reports);
  • Support side: an inventory Bot, a logistics-timeliness Bot, a finance Bot (watching the margin of every listing, producing weekly and monthly reports), and a compliance Bot (pulling compliance policies to vet listings before they go live, e.g. restrictions on magnetic products and certification requirements);
  • Closing the loop: one more Bot dedicated to weekly and monthly reports, distilling lessons from what was done right and wrong into the internal knowledge base.

Two details are worth noting:

  • Why data analysis is split into three Bots: at first all reports were stuffed into a single "operations data analysis" Bot; later the advertising data and financial data were split out into separate Bots for context isolation — because they come from a premium-listing background, they regard advertising and finance as the two most important pieces of the Amazon business and worth refining; the operations analysis Bot went back to watching traffic and listing-detail-page data and producing summaries.
  • VOC's data dilemma: Amazon originally had an SP-API interface for getting review data from your own store, but shut it down around July–August 2025, and ERPs such as Lingxing can no longer get review data either. Their current approach is to manually pull the latest reviews, store them internally, and then let Agents analyze them — he advises sellers who truly care about VOC to put more effort into reviews, since AI can mine reviews far more deeply than before.

The whole system has accumulated sixty to seventy Skills, distributed among the Bots (three to five under each Bot), and the full chain — product selection, copywriting, listing, ad strategy and placement, inventory, through to finance — flows and advances inside Feishu.

6. What Happened When Someone Copied the Framework Wholesale

After he shared this framework with friends in his community, someone copied it wholesale and pulled the copywriting, product-selection, and finance Bots into one group — whereupon the Bots spoke up one after another: "That's not my job, I'm leaving the group." The lesson is the architectural principle above: divide by task, keep boundaries clear, and don't mix Bots together in a group chat; a framework can only lend its thinking — every company's business is different, and it cannot be moved over as-is.

On "Getting Dumber" and Combining Multiple Agents

Zasi says Grok Bot has noticeably degraded in the last month or two: in September it felt so good that he wanted to move all work into it, but after using it he found the more workable setup is still combining multiple Agents — local Agents write Skills, cloud Bots execute, and things can get done on a phone; even if team members' Skills aren't polished, they can just @ the corresponding Bot in Feishu and get work done.

The Business Math: Margins, FBA, and Certification

  • Margin tactics: in the early pure-trading days, 15 points or more was no problem; the previous company, an integrated industry-and-trade operation, pursued scale alone and deliberately pressed margins below 10%, spending aggressively on ads — "precisely so competitors couldn't get in" — and reached over 200 million GMV in the second year; even at 10%, that's over 20 million in profit (all per his own account);
  • Warehousing and fulfillment: most goods go straight to FBA, with a small amount of inventory in overseas warehouses for emergencies; there isn't much need to build your own overseas warehouse;
  • Certification: for most products you can use the supplier's existing certifications and have the supply chain issue the certificates; only purely private-mold products require hiring an agency yourself;
  • Why he went out on his own: he couldn't reach agreement with the company on equity (per his own account); bosses have tried to poach him, but "going there is still just a job" — the income ceiling and sense of achievement in employment are both limited;

European Taxes: Don't Go Fully Grey

Aurora, a German seller (a Chinese team based in Germany, selling on local platforms such as TikTok, Temu, and Otto, with a product range in apparel, beauty, and 3C and their own overseas warehouse, fully certified), asked about cooperation and category preferences, and Zasi's reply brought out the barriers of the European sites:

  • Aurora added the practical details: nowadays you don't necessarily need to register in five countries; generally one company entity comes with two tax numbers (domestic + EU) — a German entity, for instance, has a German tax number plus an EU tax number; and she warned: don't go fully grey — goods you believe in with high margins must go through proper customs clearance, since going fully grey creates a lot of trouble later with taxes, bookkeeping, and filing; the German tax authorities launched an investigation targeting Chinese sellers a few years ago and banned quite a few of them, and the tax authorities know very well what Chinese sellers are up to;

Multi-Agent Coordination: Feishu as the Hub, Humans Make the Final Call

Mr. Wang, from a Feishu channel partner (with a SaaS background), asked: when a task requires multiple Agents to relay it, how do you coordinate them automatically? Zasi's answer was restrained:

  • Don't chase end-to-end automation. They are still in the polishing stage, and at key checkpoints they insist on human-in-the-loop — "in cross-border e-commerce, real money is on the line," so a person must confirm at the end; the confirmation process itself polishes the Skills and workflows and drives the rework rate down, but the final call stays with a human;
  • The system is built on Feishu more than on Grok Bot: all Agents' output goes back to Feishu, and any Agent (Grok Bot, Codex, Claude Code) can pick it up and push forward from there;
  • Mr. Wang shared his own version: he spent a week building a workbench that shows each task's execution nodes and automation results; he submits feedback on the workbench, and a GPT-side Agent captures it and distributes adjustments to the various Bots — he himself rates it a complex project: "I don't know what it will be good for in the future; it's fun."

Connecting the Tools: CLI + Skills + Swapping the Backend Behind Feishu Bots

  • Listener Ajian asked how Grok Bot connects and works with Claude, Gemini, and others. Zasi answered: use CLIs (install the Codex CLI inside Grok Bot) + use Skills to unify behavior; the Skills are managed centrally in GitHub, whoever finds a Skill lacking while executing iterates on it, and Grok Bot periodically pulls the updates; the final results are deposited in Feishu, and intermediate communication matters less than the results themselves;
  • Tiezhu added: Feishu bots can be connected to different Agent backends — there are open-source projects on GitHub that can plug Claude Code, Antigravity, Codex, and even domestic Chinese Agents into Feishu bots, so the copywriting role can be paired with Gemini or Kimi and the image role with Codex, maximizing each model's strengths by role; he also mentioned that Gemini's latest model is very strong and has become a flat replacement for Claude (all views are the speakers' own).

The Knowledge Base Must Be Able to Evolve Itself

  • Tiezhu has written a tutorial (a WeChat public-account article) on building a knowledge base based on LLM Wiki + Hermes, whose distinguishing feature is that the knowledge base can evolve itself; he will post it in the group;
  • Mr. Wang's approach: set up a "knowledge base administrator" Agent to run two quality checks — before external information is stored, it first reviews whether it is worth storing and where its value lies; obsolete material already in the base is periodically searched out and deleted;
  • Saiteka, who comes from traditional foreign trade (he built his own system to run cross-border for four manufacturers, running GEO/SEO/EDM, with customers communicating over WhatsApp), stressed a misconception about RAG: it is not the case that the more you feed it, the better — incoming documents must be deduplicated, cleaned, and denoised before the answers an Agent retrieves will get more and more accurate; his knowledge base is partitioned by manufacturer and product line (a product library, a customer-service library, etc.), and when a customer asks something, the corresponding Agent retrieves from it and a human relays the reply. He put an independent-site system live for his first client in September 2025, says the traffic is basically all brought in by GEO, and shared his 24-hour backend data: over 460 from Bing, over 200 from Google, and over 120 from Apple (the client makes laboratory glass instruments and sells to Europe and the US);
  • He also warned that product selection should first look at category barriers: for products like laboratory instruments, overseas certification costs are extremely high and European and American channels are basically occupied by three major distributors, so however good the brand, it is hard to squeeze in; categories like outdoor goods are much easier to do.

GEO: The New Traffic Entrance Mentioned Again and Again

Tim, from a brand-going-global company, shared two projects:

  • The GEO project: at his previous company, an independent site did GEO for about three months, and AI-driven traffic doubled while revenue rose by about 50% (per his own account). The key points: GEO's foundation is SEO — only once your SEO is ranked first or second among competitors does GEO become twice the result with half the effort; in the North American market the main entrance for AI traffic is ChatGPT, and they first dug out the one to two hundred specific questions customers ask AI (for example, "what is the best premium machine for a beginner to buy" or "which food processor is best for acrylic scenarios"), then optimized, for those questions, the channels ChatGPT likes to crawl — their official site, Reddit, YouTube, Wikipedia, and so on (at the time they didn't even have a Wikipedia entry, and hurried to add one);
  • The VOC public-sentiment system: pull user reviews from all channels — Amazon, various social platforms, Reddit, and so on (from both buyers and non-buyers) — into one place, use a large model to tag and classify them (pre-sale questions, after-sale questions, questions about a particular product), then route them to after-sales tickets or pre-sales inquiries; the accumulated data is of great value for later product selection and product iteration;
  • The host added: at a GEO conference that had just ended, a speaker shared that the video length Doubao crawls the most is 5-minute videos (not the long videos people usually assume); overseas GEO practitioners buy keywords and do PR, often thousands of keywords at a time. In an environment where traffic keeps getting more expensive, GEO can still pull in relatively low-cost traffic.

Closing in One Sentence

The most valuable part of this session is not any tool trick, but two judgments: first, the ceiling of an Agent team depends on the data APIs you feed it and the Skills you accumulate, not on the model itself; second, the more a business involves real money, the more "a human makes the final confirmation" must be written into the process.
